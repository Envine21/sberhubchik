# Практика: tool-calling harness

В этом комплекте нужно восстановить небольшой Python harness, который принимает
вопрос, позволяет модели запросить арифметический инструмент и возвращает итог.
Работайте с одной причиной за раз: сначала опишите наблюдение и гипотезу,
покажите, какое место кода подтверждает гипотезу, затем внесите изменение и
повторите тот же сценарий.

## Подготовка

Нужен Python 3.11 или новее и доступ к DeepSeek API.

```text
python -m pip install -r requirements.txt
```

Создайте локальный файл настроек из шаблона. В PowerShell:

```powershell
Copy-Item .env.example .env
```

В bash:

```sh
cp .env.example .env
```

В `.env` укажите `DEEPSEEK_API_KEY=свой_ключ`. Клиент ищет этот файл рядом со
своим исходным файлом.
Уже заданная переменная окружения имеет приоритет над значением из `.env`.
Настоящий `.env` не добавляйте в Git и никому не передавайте.

## Единственный способ запуска

Вопрос передаётся обязательным позиционным аргументом. Модель по умолчанию —
`deepseek-flash`; отдельный выбор модели в учебном запуске не предусмотрен.

```text
python run.py "Сложи 18 и 24"
```

Один запуск отвечает на один вопрос. Внешний клиентский предохранитель допускает
не более восьми запросов модели на этот вопрос. При превышении программа должна
закончиться краткой технической ошибкой; этот предел не заменяет ограничение
шагов из второй части.

Ожидаемый смысл ответов для базовых сценариев:

| Вопрос | Ожидаемый результат |
| --- | --- |
| `Сложи 18 и 24` | В финальном ответе есть `42`. |
| `Сначала сложи 18 и 24, затем раздели результат на 6` | В финальном ответе есть `7`; промежуточные действия выполнены последовательно. |
| `Проверь работу инструмента деления: раздели 12 на 0` | В выводе появляется `Ответ:` с объяснением ошибки от модели, а не аварийная строка `Ошибка:`. |
| Обычный текстовый вопрос | Модель отвечает текстом; арифметический инструмент без причины не вызывается. |

Формулировка финального текста может отличаться. Важны результат, порядок
необходимых действий и контролируемое поведение ошибки.

## Часть 1. Восстановление базового протокола

В коде есть нарушения протокола. Найдите их, исправьте по одной
причине и после каждого изменения повторяйте подходящий базовый сценарий. Не
объединяйте несколько исправлений в одну попытку.

Исправленный harness должен:

- выполнять арифметику через доступные инструменты, а не подменять её текстовым
  ответом;
- выполнять зависимые вычисления в нужной последовательности и использовать
  результат предыдущего действия в следующем;
- передавать модели результаты выполненных действий, чтобы она могла выдать
  осмысленный финальный ответ;
- завершать обычный вопрос финальным ответом модели после необходимых действий;
- передавать ошибку инструмента модели, чтобы финальный ответ объяснял проблему
  пользователю, а процесс не завершался необработанным исключением.

Секреты, полный запрос к API и необработанный traceback в пользовательский ответ не
включаются. Отсутствие вызова инструмента в отдельном ответе модели само по
себе не доказывает ошибку Python-кода — опирайтесь на воспроизводимое наблюдение и проверку истории.

## Часть 2. Домашнее задание

### CR1. Ограничение шагов

Добавьте положительный целочисленный `max_steps`. Один шаг — один запрос к
модели; несколько вызовов инструментов в одном ответе считаются одним шагом.
При достижении лимита новый запрос не отправляется, а выполнение завершается
с причиной `max_steps`. Последний результат инструмента нельзя выдавать за
финальный ответ модели. Успешное завершение и остановка по лимиту должны
быть различимы.

### CR2. Логирование

Записывайте структурированные события: отправка запроса, получение ответа,
изменение истории, начало выполнения инструмента и ошибка. Указывайте
идентификатор запуска, номер шага, стадию и статус, а также идентификатор
вызова и длительность, когда они известны. Ключи, токены и другие секреты
не должны попадать в журнал. Полные запросы и пользовательские сообщения
по умолчанию скрывайте или сокращайте.

### CR3. Инструменты `multiply` и `subtraction`

Сделайте `multiply(a, b)` и `subtraction(a, b)` доступными модели как
инструменты. Неверные типы, лишние поля, недоступная операция и неизвестное имя
должны иметь различимые контролируемые результаты; прямой вызов не должен
обходить проверку доступа.

### CR4. Таймауты модели и инструментов

Добавьте отдельные ограничения времени: `model_timeout` для запроса к модели
и `tool_timeout` для выполнения инструмента. При превышении времени выполнения
инструмента модель должна получить контролируемую ошибку, связанную с исходным
вызовом. При таймауте модели сообщение от инструмента не создаётся. После
таймаута не должно быть неконтролируемого повторного запуска. Диагностика
должна явно различать эти два случая.

### CR5. Единая конфигурация

Соберите лимиты, таймауты и список разрешённых инструментов в единую
конфигурацию. Эти значения можно изменять во время работы программы, и такие
изменения должны влиять на её дальнейшее поведение.

### CR6. Инструмент чтения файла

Создайте инструмент, который принимает путь к файлу, читает его и возвращает
содержимое модели.

### CR7. Ограничение доступа к файлам

Для инструмента чтения файла нормализованный путь должен оставаться внутри
разрешённого `workspace`; попытка выйти за его пределы отклоняется. Ошибка
должна сохранять исходный идентификатор вызова и не раскрывать содержимое
закрытого файла. Путь к `workspace` задаётся в единой конфигурации.
